# 飞书多用户协作工作流

妖玉影视团队通过飞书与 Hermes 协作：多项目并行（伏妖记/犬子无双/手心人等），每个项目涉及多个群/话题/私聊/用户。本 skill 定义 bot 在飞书多用户场景下的行为规则。

## 数据位置

| 数据 | 路径 |
|---|---|
| 会话路由表 | `Obsidian Vault/_hermes/会话路由.json` |
| 成员名单 | `Obsidian Vault/_hermes/成员名单.json` |
| 评论会话记忆 | `Obsidian Vault/_hermes/评论会话/<项目>:<open_id>.json`（2026-08-07 起迁入 vault，此前在 hermes home `comment_sessions/`，已迁移+清理） |
| 项目记忆 | `Obsidian Vault/_hermes/项目记忆/<项目>.md`（2026-08-07 起 bot 实时沉淀——IM 消息管线 run.py 钩子 + 文档评论管线双通道写入，按日去重，每日≤5 条） |
| 成员画像库 | `Obsidian Vault/成员画像/<真名>.md`（frontmatter 含 open_id/角色/专长/参与项目/updated/tags: [飞书协作, 成员画像]） |
| 飞书协作记忆 MOC | `Obsidian Vault/_hermes/飞书协作记忆MOC.md`（图谱枢纽，`#飞书协作` tag 成组） |
| 项目知识 | `Obsidian Vault/<项目名>/`（剧本/分场分析/复盘/自审报告） |

## 1. 会话路由（判断当前会话属于哪个项目）

收到飞书消息时按顺序处理：

1. **查路由表**：从消息 session_key 提取 chat_id（`oc_xxx`）和 thread_id（`omt_yyy`）
   - 先查话题级 key `oc_xxx:omt_yyy`，命中即用
   - 再查会话级 key `oc_xxx`，命中即用
2. **未命中 → 自动识别**：用消息内容 + 项目词典（路由表 `项目词典` 字段）判断归属项目
   - 判断成功 → 写入路由表（`路由[chat_key] = {project, space}`），下次免识别
   - 有歧义/不确定 → 只问妖玉一次，答案写入路由表
3. **话题级细化**：若会话级路由是泛值（如协作群归「协作」）但当前消息明确指向某项目（命中词典）且该话题（`oc_xxx:omt_yyy`）未登记 → 将**话题级 key** 登记到具体项目（`路由["oc_xxx:omt_yyy"] = {project, space:"话题"}`），后续该话题消息直接精确路由
4. **妖玉修改**：`@bot 把<会话>归到<项目>` → 更新路由表

路由确定后：加载该项目 Vault 目录的项目主文档 + 复盘（项目上下文注入），再处理请求。
**降级**：若 Vault 无对应项目目录（如会话标题类项目：终焉圣骸/深渊古堡等），不加载文档直接对话，并在路由表该项目标注 `"has_docs": false`；Vault 项目目录不存在的识别结果仍正常写入路由表（会话归属有效，只是无项目文档可加载）。

## 2. 成员画像（按人个性化）

- **读取**：消息发送者 open_id → 在 `成员画像/` 找对应画像（frontmatter 有 open_id 字段）。群消息用 `[sender name]` 前缀名匹配画像文件名
- **沉淀规则**（自动）：
  - 观察到**明确**偏好/事实（沟通风格、偏好时段、专长、重要习惯）才写
  - 同一天同类观察合并为一条（去重），不设条数上限
  - 不确定的不写；写回更新 `updated` 字段
- **妖玉可审**：`@bot 画像变更报告` → 列出最近沉淀；`@bot 王五的画像` → 展示指定画像
- **应用**：回复前先看发送者画像（沟通风格/专长），个性化语气和内容；被问到"该让谁做"时按专长推荐人选，但派活由人在飞书直接 @

## 3. 任务协作（人在飞书，kanban 归 AI）

**铁律：派活是人的事，bot 不做流程中介。** 飞书原生 @ 就是最好的分配+通知：`@王五 把这个做了` 一步到位。bot 介入建任务/认领/完成闭环 = 纯摩擦，禁止。

- 妖玉/成员要派活 → 直接 @ 具体人，**不要**让 bot 建任务
- kanban（`hermes kanban`）只用于 **AI 自动化任务**（dispatcher 多 agent 协调、cron 派生的执行任务），不用于人协作待办
- bot 被问「有什么任务/看板状态」时，可展示 kanban 中 AI 任务的记录（只读回答，不创建）
- 话术修正：
  - ~~`@bot 给@王五 派任务：<内容>`~~ → 引导：直接 @王五 分配
  - ~~`@bot 认领<任务>`~~ / ~~`@bot 完成任务`~~ → 人在飞书跟进即可
  - `@bot 项目任务看板` → 只读汇总 AI 任务状态（保留）

## 4. 权限（admin / worker）

- **妖玉（admin）**：全量——改路由、管理画像、派任何任务、全局记忆写入
- **成员（worker）**：受限——查项目、领任务、交任务、查自己的画像、读项目文档
- 全局记忆（MEMORY/USER）写入门禁已由 `agent.system_prompt` 控制（只允许妖玉），本 skill 不绕过

## 5. 限制与节流

- 飞书 rate limit 5 QPS / 100 QPM：批量消息要合并发送，避免瞬时多条
- 共享话题模式：任何人发言打断当前任务——长任务用任务窗口约定（派活时说明预计耗时）
- 路由表是软机制：识别错误靠妖玉修改兜底

## 6. 协作健康检查（2026-08-07 起）

统一健康检查脚本 `scripts/feishu-collab-health.py`（IM + 评论双通道统计）：

```bash
python3 ~/AppData/Local/hermes/scripts/feishu-collab-health.py [hours]  # 默认 48h
```

检查面：①成员活跃度（IM 会话 + 评论线程合并，按人）②路由覆盖（活跃会话是否登记进 会话路由.json）③画像覆盖（成员名单 vs 画像文件 open_id）④项目记忆（文件 + 每日每项目≤5 条限额检查）⑤评论线程明细。

自动监控：每周日 22:00 cron「飞书协作健康检查」跑 168h 窗口，异常告警到妖玉 DM；每日摘要 cron（88ab7ff66681）已纳入评论通道采集 + 画像落库步骤。

**路由表维护要点**：
- session_key 格式：`agent:main:` 前缀去掉后为 `feishu:dm:oc_xxx` / `feishu:group:oc_xxx[:omt_yyy]`，话题级 key 有 `:omt_` 和 `:om_x` 两种后缀，查路由时剥后缀回退会话级
- DM chat_id 归属按 user_id 反查（state.db sessions 表），不能凭路由表已有登记猜
- 新成员/新会话出现后，用健康脚本「路由未登记」列表补登记

## 验证清单

- [ ] 新私聊首次消息 → 路由表新增条目
- [ ] 已知群消息 → 不重复识别，直接用路由
- [ ] 成员偏好被沉淀 → 画像文件出现新条目（同类观察合并）
- [ ] 成员要派活时，bot 引导直接 @ 具体人（不建任务）
