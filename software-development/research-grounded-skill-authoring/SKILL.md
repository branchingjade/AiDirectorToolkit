# 研究驱动的 Skill 构建工作流

当用户要求 skill 内容"有跟脚/有依据/不凭空写"（如"研究所有知名导演和高分电影""标准行业格式""所有内容要有来源"）时，按本工作流执行。它确保产出的 skill 每条规则都有可验证来源，而不是模型凭空生成。

## 触发场景

- 用户要求新建/升级 skill，强调内容要有来源、有跟脚
- 涉及行业规范、权威理论、知名案例的 skill（影视/编剧/导演/格式类最常见）
- 用户说"深入研究 X""发掘实际案例""不能马虎"

## 核心原则

1. **每条规则带来源**：理论/规范/案例必须来自真实抓取的页面，标注 URL + 原文摘录
2. **不编造来源**：抓不到的如实说"未找到"，绝不用模型记忆冒充
3. **先研究后写**：skill 正文是研究的提炼，不是凭空创作
4. **一手来源 > 二手转述**：能抓原文全文就别满足于百科条目。实测：抓 McKee《Story》全书原文（779K 字符）后，控制思想/场景/节拍/缺口定义全部是原文，跟脚强度远超维基转述——优先搜"原书全文/官方文档/法规公报"，其次才用维基/百科
5. **英文维基是主体，中文维基常是空壳**：中文维基条目经常是重定向页或内容极少的 stub（实测黑泽明/电影剧本中文条目均如此），英文维基才是内容主体——优先抓英文维基再翻译

## 工作流（五步）

### 1. 建立研究目录 + 初始化 ledger

```bash
mkdir -p _work/<项目>/pages
S="<hermes>/skills/research/grounded-citations/scripts/sources.py"
python "$S" reset   # 每轮研究重置，编号从 1 开始
```

### 2. 并行派子代理分片研究（delegate_task 批量）

每个子代理负责一个独立切片（如：格式规范 / 西方导演 / 东方导演 / 剧本分析），context 里必须写死：

- **产出文件路径**（绝对路径，如 `C:/.../_work/<项目>/<研究主题>.md`）
- **来源要求**："每条结论标注来源 URL（真实抓取过的），抓取页面正文存到 pages/ 下"
- **诚实要求**："抓不到就如实说明哪些成功哪些失败，不要编造"
- **中文回复**

### 3. 主线程备源（关键防超时策略）

子代理经常在 600s 超时或 50 次工具调用上限处中断——**资料已抓但笔记未落盘**是常态。对策：

- 派发后主线程立即自己抓 3-5 个最关键来源做备用（如维基核心页面）
- 子代理超时后：**从 pages/ 目录续跑**——原始资料都在，主线程直接读原始文本提取要点补写笔记，成果不丢
- 实测：东方导演子代理超时但 9 位导演原始页面都在，主线程从原文提取手法补写了完整笔记

### 4. 多子代理写同一文件冲突

- 子代理的目标文件名可能与主线程的产出冲突 → 主线程产出改名为 `XX-主线程.md`，让子代理写原名
- 用 `mv` 改名，避免互相覆盖

### 5. 汇总验证 + 挂载 + 发布

```bash
# 注册所有来源（从笔记提取 URL 批量 add）
python "$S" add <url1> <url2> ...
# 生成 Sources 块（verify 硬性要求）
python "$S" render --replace-in <笔记.md>
python "$S" verify <笔记.md>   # citations OK 才算过
```

- 验证通过后：研究文档 `cp` 进 skill 的 `references/` 目录
- skill 正文加「参考研究文档」一节指向它们
- 版本号升级 → skill-publish 三步（同步正本 → tag → Release）

**发布顺序铁律（2026-08-09 实测）**：`git push` 被拒时**先 `git pull --rebase` 解决，再打 tag**——若先打 tag 再 rebase，已推的 tag 指向旧 commit（Release 建在错误历史节点）。修正：`git tag -d X && git push origin :refs/tags/X` 删旧 → rebase 后重建 tag → 重推 master+tag → `git ls-remote --tags origin | grep X` 验证指向新 commit。

**严重分叉仓库的安全推送（2026-08-17 实测：本地与远程分叉 >60 提交时）**：本地与远程已深度分叉（远程领先 N 提交、本地领先 M 提交、merge-base 极旧、本地含远程没有的大量文件/工作区未提交改动）时，**直接 rebase 会产生海量冲突、force push 会丢远程历史**。安全做法——worktree + cherry-pick，本地工作区零接触：

```bash
# 1. 基于远程最新开临时工作树（⚠️ MSYS 下 /tmp 会转成 C:/tmp，用 git worktree list 查实际路径）
git worktree add C:/tmp/<repo>-push origin/master
cd C:/tmp/<repo>-push
# 2. 把要推的本地提交 cherry-pick 到远程线之上；冲突通常是"远程旧版 vs 本地新版"，取 --theirs 即可
git cherry-pick <本地commit>
git checkout --theirs <冲突文件> && git add <冲突文件>
git -c core.editor=true cherry-pick --continue
# 3. 推送（HEAD:master 把临时树提交推到远程 master）
git push origin HEAD:master
# 4. 清理
cd <原仓库> && git worktree remove C:/tmp/<repo>-push --force && git worktree prune
```

- **推送后本地保持原状**：本地 master 不必动——本次提交已在远程（`git log --oneline origin/master -1` 验证 + `git show origin/master:<文件> | grep ^version` 验证内容）。**⚠️ 不要 `git reset --soft origin/master`**：本地含远程没有的文件（如本地是完整 skills 目录、远程是子集仓库）时，soft reset 会把几百上千个本地独有文件 staged 成 `A` 状态，几乎不可逆地污染索引——误操作后用 `git reset --mixed <原HEAD>` 恢复
- **验证闭环**：push 后查远程树 `git ls-tree origin/master` 确认目标目录存在、关键文件版本号正确，再向用户报告

### 6. 评估既有 skill → 缺口清单 → 系统补齐（用户要求"拉高水平、拒绝短板"时）

构建完成后，用户会要求"从专业角度和观众交付评估现在的 skill"。评估与补齐按此循环：

**评估框架（两个维度分开看，结论会不一样）**：
- **专业角度**（创作层）：对照行业理论体系找缺口——编剧（人物塑造/类型惯例/对白/序列副线）、导演（动作编排/转场/场景镜头逻辑/连续性）
- **观众交付**（制作层）：从分镜到成片链路逐环节检查——生成预算 / 剪辑方法论 / 跨段一致性 / 声音链路 / 成片验收。**"分镜是设计图，电影是盖好的楼"——创作引擎完备 ≠ 交付引擎**
- 输出分层评级表（如：创作层 ★★★★ / 交付层 ★★），短板一目了然

**补齐方法（缺口清单驱动）**：
1. 评估产出缺口清单（创作层 + 制作层 + 验收层）
2. 每层派独立子代理研究（创作层-编剧 / 创作层-导演 / 制作层 / 验收层 四切片）
3. 每缺口对应 skill 新增一个章节（如编剧二·六、导演三·六、导演四·五制作交付）
4. 制作层结论必须标注【计算】/【可验证】/【推断】——官方文档能覆盖工具能力，但"整片流水线"实操规范多来自行业实践与推断，逐条标注不装数据

**用户尺度**：修复时"有条理有方法、拉高水平、拒绝短板、不用计较成本"——研究要全、缺口要清零，不省子代理数、不砍研究范围。

### 7. 发布后系统性自检（每次构建/升级后必跑）

用户会要求"系统地完善地自检"。自检是独立一轮，不是发布附属——实测每次都能抓到真 bug。十二项清单：

1. **版本号 frontmatter=正文**：`grep "^version:" SKILL.md` 与正文标题 `# XX vX.Y.Z` 数字一致（注意 frontmatter 无 v 前缀、正文有，比对数字即可）
2. **本地 vs 正本全量 diff**：所有 SKILL.md + references/ 文件逐一 `diff -q`（26 文件级）
3. **references 双向一致性检查（最高价值，实测抓到 2 个真 bug）**：
   - 方向 A：正文引用《X.md》但文件缺失 → 复制文件过来（引用正确、缺文件）
   - 方向 B：参考列表有文件但正文从未引用 → 从列表删除（纯冗余）
   - 实现：Python 正则 `《([^》]+\.md)》` 提取正文引用 set，与 references/ 实际文件 set 做差集。**不要用 sort 命令**（中文文件名 sort 报 "string comparison failed"，用 Python set 操作）
   - 实测案例：AI电影编剧 引用《导演研究-东方.md》但文件只在导演那边 → 复制；AI电影导演 参考列表有《高分剧本分析/格式规范研究》但正文无引用 → 删除
4. **内部锚点断链**：`grep -oE "\[[^]]+\]\(#[^)]+\)"` 提取锚点链接，核对目标标题存在（中文锚点：标题去标点、数字不转英文）。**⚠️ 改章节标题必须同步 grep 引用旧锚点的位置**（2026-08-17 实测：AI短剧导演助手「平台约束参考（Seedance 2.0）」→「（2.5）」后，SKILL.md:17 的 `#四平台约束参考seedance-20` 变死链——GitHub 风格锚点随标题变化，标题改了锚点就失效）。验证锚点是否真的命中：脚本对括号/破折号（em dash）的锚点会误报缺失，命中后先核对实际标题再判断
5. **短剧污染残留复查**：发布后仍要 grep 全文扫（"同短剧版"/"见 XX助手"），剩余"短剧"字样逐条判断是门禁选项/对比说明（正当）还是内容依赖（清除）
6. **references 挂载完整性**：skill_view 确认 linked_files 全在、readiness_status=available
7. **git 双工作区干净**：正本仓库 + 用户工作区 `git status --short` 均空
8. **tags 齐全**：`git tag | grep <前缀>` 确认每次升级有对应 tag
9. **临时目录清理**：`rm -rf _work/<项目>` 不存在
10. **delegation 日志清理**：`cache/delegation/live/deleg_*` 和 `subagent-summary-*.txt` 删光（用户会问"还有个后台子代理"——真相往往是超时任务日志残留，不是活跃进程）
11. **进程核查**：process list 空 + `tasklist | grep python` 只余 Hermes 组件（gateway/serve/runtime）与无关进程，无子代理残留
12. **自检修复也要同步发布**：自检发现的 fix 走同一提交链路（同步正本 → commit → push），不要只改本地
13. **旧结论快照失效检查（版本升级后必查，2026-08-17 实测）**：升级某 skill/模型版本后，grep 知识库 references/ 里**引用旧版本结论的存档文档**——它们写死的「以 vX.Y 为准」「不改变 vX.Y」类结论会被升级推翻（实测《Seedance2.5官方理解.md》原「不改变 AI提示词助手 v1.5.1 约束主本」在 2.5 升级后失效）。处理纪律：**历史留档不改原文，在头部加 📌 更新注记**（注明新结论+哪些差异点已采纳、哪些仍以主本为准）——既防后续引用误导，又保留取证真实性

**自检报告格式**：通过项表格（# 检查项 结果）+ 修复项表格（问题/根因/修复）。根因要挖（如"早期加电影形态的残留引用，后来方向变了电影独立成树"），不要只报症状。

### 7.5 存量知识库维护审计（非构建场景，用户要求"客观分析、做规划、有依据"时）

知识库已建成后，用户要求"继续完善/客观分析/做规划"时，跑存量审计七查（2026-08-08 实战，全部抓过真 bug）：

1. **资产声称 vs 磁盘核对**：frontmatter description 的数字声称（"141部/59份/43行"）逐一 vs `ls | wc -l` 实际数——声称漂移是高频 bug
2. **版本号漂移检测**：SKILL.md 索引版本 vs 各题材密码/文件实际版本做差集（实测抓到 6 处滞后——回测升级后索引没同步；含"文件头版本行未随内容升级"的变体：内容已加新回测章节但 header 仍写旧版）
3. **零入口资产检测**：所有资产文件名 vs SKILL.md 全文提及做差集——文件存在但任何索引/检索表/招式表都不提及 = 写戏时永远找不到（实测 141 卡中 10 张零入口，内容质量正常，纯缺入口）
4. **引用双向一致**：`《X.md》`/`` `X.md` `` 提取引用 set vs references 实际文件 set 差集——⚠️ 带路径引用（如 `题材密码/xx.md`）必须 join 完整路径再 exists 判断，纯文件名比对会误报 13 处
5. **索引断链**：索引表提及的导演/资产名 vs 实际文件（实测彼得·威尔被导演索引引用但无对应文件——修法：改指向"查 XX技法卡片"）
6. **孤儿源稿**：references 根目录散落原料 txt——`grep -rl 文件名` 查被引用数；0 引用 + 内容在 pages/ 有副本（`diff <(tr -d '\r' < a) <(tr -d '\r' < b)` 忽略行尾比对内容一致）→ 可安全删除，删除后 `ls` 确认根目录纯净
7. **使用率可见性**：knowledge-usage.py 从 state.db 查 skill_view 结果——只做可见性（高频=深化方向，低频=引用缺失补入口），不做清理依据（用户定论：知识库=蒸馏的知识，0 次加载≠该清理）
8. **消费方接入审计（新增资产层后必查，2026-08-08 实测抓真 bug）**：知识库新增资产层（如第五层制作学科库）后，**只查知识库自身一致性不够**——查所有消费该知识库的 skill（AI电影编剧/导演/短剧编剧/短剧导演/提示词助手）的引用是否覆盖新层。实测 5 个创作 skill 的知识库先行流程都只到「题材密码+技法卡片」，完全不知道学科层存在 = 「建了没用」地基断裂。修复：每个消费 skill 的流程段加对应步骤（导演 skill 加光影/构图/声音/剪辑/调色/视效，编剧 skill 加服化道/美术/色彩/声音，提示词 skill 加全部学科密码的 AI 提示词对接节）+ 版本 patch 升级 + 同步正本。
9. **下游 skill 过时数字扫描（不只是知识库自身声称）**：`版本号/数字声称漂移` 不只发生在知识库自己的 frontmatter——**消费方 skill 内置的快照数字同样会过时**（实测 AI短剧导演助手写「大师技法卡片37部」，实际 141——37 是早期快照）。自检时 grep 所有消费 skill 的 `技法卡片N部/导演N位/题材密码N套/制作学科库N份` 类声称，与实际磁盘数核对；「招式速查 16 条」是 skill 内置默认在场子集（知识库 51 条精选 16 条常驻）属设计值，别误改。

**修复优先级**：一致性（版本/数字声称）> 入口（零入口资产补检索表/招式表）> 结构纯净（孤儿清理）> 深化补缺（有卡片无深化的导演从存量合成）。每项修复后跑一次全量自检确认无新断链。

**布局模式（用户拍板"题材、导演等知识是布局，不能等项目"）**：布局不依赖真实项目需求，主动铺开。
- **快赢项**：有技法卡片但无导演深化文件的导演 → 从存量合成深化文档（零新抓取：读导演卡片+技法卡片+研习报告合成，全部论断带来源编号，诚实声明"零新抓取"）——周星驰案例（功夫/大话西游两张卡+研习报告合成 13KB 深化）
- **研习轮**：完全无素材的缺口导演 → 先写规范.md（产出物结构/来源纪律/工作目录）→ delegate_task 批量派发（每子代理一个导演：读模板→抓取→pages/ 存档→按模板写两文件），缺口盘点依据=创作参照系相关性+存量素材+电影史地位
- 布局清单输出：梯队表格（快赢/研习）+ 每项依据 + 成本标注，用户拍板后执行

**全链条核对（规划遗漏检测，2026-08-08 被用户"还有遗漏的吗"点破后确立）**：用户点名若干维度（如"声音、色彩、美术、服化道"）要求做规划时，**不能只按点名维度规划**——按行业制作全链条核对一遍（影视 = 前期→视觉设计→拍摄→后期→声音），逐环节问"这一环有知识资产吗"。实测 v2.0 规划 6 学科全在视觉设计/拍摄轴，用户一句"还有遗漏的吗"点出后期三件套（剪辑/调色/视效）全漏——v2.1 修正为 9 学科覆盖全链条。产出核对矩阵：`阶段|维度|现状|规划`，直接向用户展示，主动暴露遗漏而不是等用户追问。

**制作学科库模式（第五层新资产类型）**：学科密码 = 定义谱系/核心语法/范本实证/常见坑/自检清单/AI提示词对接 八节，与导演卡片**正交**——导演卡片管"谁的手法"，学科密码管"这个领域的语法"（导演卡片按人组织、学科密码按专业组织，互为正交索引）。执行要点：①先写 `00-模板规范.md`（文件结构/引用约定/质量纪律）再并行派子代理；②每子代理一份密码，素材路径全部写死（知识库 SKILL.md 招式表/导演卡片/技法卡片/AI导演约束章节/Seedance 理解）；③学科密码管专业领域，叙事/题材层归题材密码，不重复。

### 7.8 本地 vs 正本全量 diff 的 CRLF 陷阱（2026-08-09）

`filecmp.cmp` 或 `diff` 报 N 个文件「内容不同」时，**先归一化换行符再判真差异**——git autocrlf 会把 LF 转 CRLF 入库，本地是 LF，23 个文件「不同」全是换行符差异、内容零差异：

```python
with open(a, encoding='utf-8') as f: ta = f.read().replace('\r\n','\n').replace('\r','\n')
with open(b, encoding='utf-8') as f: tb = f.read().replace('\r\n','\n').replace('\r','\n')
same = ta == tb  # 归一后一致 = 仅换行符差异，非内容差异
```

先排除换行差异，剩下的才需要逐字 diff 找第一处不同。
