# 剧本审读（Script Review）

对已有影视剧本（尤其长剧/短剧文档）做整体阅读、结构拆解与质量评估。

## 前置：从飞书拉取剧本

剧本常以飞书文档形式交付。**但用户直接在飞书聊天里发 docx 时，文件缓存在 `AppData\Local\hermes\cache\documents\`，`read_file` 能直接自动提取全文分页读完（实测 5114 行 240KB 剧本三页读完，中文 docx 无二进制误判），跳过飞书拉取流程。** 只有剧本以飞书云文档（URL/token）交付时才走下面的 lark-cli 拉取。加载 `lark-doc` skill，用：

```bash
mkdir -p _work
LARKSUITE_CLI_NO_UPDATE_NOTIFIER=1 LARKSUITE_CLI_NO_SKILLS_NOTIFIER=1 \
  lark-cli docs +fetch --doc "<URL>" --doc-format markdown --format json > _work/script.json
```

也可以直接用配套脚本一步完成拉取+落盘：`python scripts/fetch_feishu_script.py <doc_url> [workdir]`（输出 `script.md`，并打印字符数）。

**陷阱：`--scope outline` 对剧本类文档不可靠。** 剧本的集数/章节多为普通段落或加粗文本，不是标题块，outline 只返回极少数标题（实测 50 集剧本 outline 仅命中 3 个标题块，且层级错乱）。结构未知的长剧本**直接全量 fetch**，不要用 outline 探测后按标题切片。

## 本地分页阅读

全量内容保存为本地 md，**分页读完再总结，不中途截断**（head -c 截断只适合快速探测）：

```bash
python -c "
import json
d = json.load(open('_work/script.json', encoding='utf-8'))
content = d['data']['document']['content']
print('字符数:', len(content))
open('_work/script.md', 'w', encoding='utf-8').write(content)
"
# 分页读：python -c "t=open('_work/script.md',encoding='utf-8').read(); print(t[起点:终点])"
```

**陷阱：read_file 可能把大体积 UTF-8 中文文件误判为二进制**（实测 100KB 无 null 字节的 .md 也被报 "Binary file"）。遇到 "Binary file" 时直接用 python 分页打印代替 read_file，不要反复重试 read_file。

## 飞书评论审读（把点评落到文档右侧）

用户要求「在文档右侧评论里给点评/吐槽/优化建议」时（编剧审读、批注、review 场景），在拉取全文（见上）之后：

1. **拿 block id 映射**：`lark-cli docs +fetch --doc "<URL>" --detail with-ids`（XML 里 `<p id=...>`/`<h1 id=...>`），解析出 id→文本映射。评论挂载点以 block id 为准，不要凭文本搜——多处相同文本会挂错位置。

2. **逐条挂局部评论**（Review 场景禁止把问题合并成一条全文评论）：
   ```bash
   lark-cli drive +add-comment --doc "<URL>" --block-id "<BLOCK_ID>" \
     --content "$(cat c1.json)"
   ```
   最后加一条全文总评（不带 `--block-id`）。评论格式：**点评/吐槽 + 优化建议 + 为什么**（用户明确要求每条都要有「为什么」）；每条开头用【类型】标注（【结构问题】【逻辑漏洞】【人物】【对白】【格式】【亮点】），100-200 字精炼。

   **⚠️ JSON 生成铁律（2026-08-07 实战教训）**：`--content` 参数**禁止手拼 JSON 字符串**——评论文本含引号时极易破语法（ASCII 直引号 `"` 未转义必炸；中文弯引号 `""` 无需转义）。一律用 `json.dumps` 生成，评论先落盘再挂：
   ```bash
   # 每条评论写 cN.txt → 转成 cN.json → 验证 → 挂
   python -c "import json; print(json.dumps([{'type':'text','text':open('c1.txt',encoding='utf-8').read()}], ensure_ascii=False))" > c1.json
   python -m json.tool c1.json > /dev/null && lark-cli drive +add-comment --doc "<URL>" --block-id "<BLOCK_ID>" --content "$(cat c1.json)"
   ```
   或者短评论内联：`--content "$(python -c 'import json,sys; print(json.dumps([{"type":"text","text":sys.stdin.read()}], ensure_ascii=False))' <<< '评论内容')"`。写文件被 JSON 校验拒绝 = 语法问题，修正重写后再挂，不要跳过校验硬推。

3. **陷阱**：
   - 部分 block 挂评论报 `1069301`（General operation failure，与内容无关，短内容也一样）→ 换相邻 block 挂，位置仍准确。
   - **评论无法删除**（`drive.file.comments` 只有 batch_query/create_v2/list/patch，无 delete）→ 测试评论/废评论用 patch 标记已解决折叠：
     ```bash
     lark-cli drive file.comments patch --params '{"file_token":"<TOKEN>","file_type":"docx","comment_id":"<ID>"}' --data '{"is_solved":true}'
     ```
   - skill 文档里的 `+list-comments`/`+resolve-comment`/`+batch-query-comments` 等 shortcut 可能不存在（CLI 版本差异）→ 原生命令兜底：
     ```bash
     lark-cli drive file.comments list --params '{"file_token":"<TOKEN>","file_type":"docx","page_size":100}'
     ```
     返回的 `quote` 字段是评论引用的段落文本，可用于查已有评论、避免重复评。
   - **Windows 下 python subprocess 找不到 lark-cli**（lark-cli 只存在于 bash 环境）→ 批量挂评论用 bash 脚本循环执行，不要用 python subprocess。

4. **定期审读 cron 模式**（用户说「定期帮编剧分析」时）：
   - 基线存档：把最近一次 fetch 的 markdown `cp` 到固定路径（如 `~/AppData/Local/hermes/cron/output/<项目>_last.md`）
   - cron prompt 内：拉取 → `cmp -s` 对比基线 → **无变化则一句话简报结束（不评论、不改基线）**，有变化才审读+挂评论 → 更新基线
   - 单轮评论控制在 8 条以内，只挑最重要的；查已有评论避免重复评
   - **知识库先行（2026-08-10 用户拍板，伏妖记审读 cron 实战验证）**：审读必须用「妖玉影视知识库」的尺子说话，不是凭感觉——cron 挂载知识库 skill（招式速查 51 条+场景检索表+题材密码索引自动加载）；按题材必读对应题材密码（如志怪→`references/题材密码/志怪题材密码.md`，妖是照镜/执念即妖/学人的别扭/被迫的恶使爱成立）；审到具体场景类型查检索表定位大师卡片；每条点评带依据标注（【题材密码·X】【卡片·片名】【招式速查·X】），禁止无依据泛泛意见；知识库先行验证法=可优化就落地成评论、已达标明确说达标（不硬挑毛病）
   - **术语纪律（2026-08-10，国风/志怪项目）**：结构描述用起承转合/拍/信息一层层揭开，禁用三幕/建置/对抗/弧光/Chekhov's Gun 等西方教材术语命名；西方理论（Syd Field/McKee）只作思考跟脚不用于对外命名；评论/简报出现西方术语=不合格重写

## 深度打磨模式：逐场三关审查 + 分支管理（2026-08-06 实战验证）

用户说「打磨剧本」「通读终稿」时，不是修 bug，是**逐场过三关**：

### 三关审查（每场必过）

1. **合理性**：逻辑漏洞、设定矛盾、因果断链（重点查跨场一致性：道具位置、角色认知、时间线）
2. **精彩度**：该更精彩但没做的——平淡段落、未兑现的伏笔、可强化的节拍
3. **可能性**：这场还有没有别的做法？**每场至少给 2-3 个备选方案**，不只改，要论证"为什么现在的方案赢/输"

### 分支管理（创作决策留档）

像 git 分支一样管理创作决策，新建 `分支管理.md` 随项目走：

```
## 第N场 [场名]
- **三关审查**：合理性/精彩度/可能性各结论
- **备选方案表**：| 方案 | 内容 | 优势 | 代价 | 决策 |
- **决策记录**：为什么选当前 / 换掉损失什么 / 什么条件下切分支
```

- 主线=锁定剧本；每个决策点=可切换分支，备选方案不丢失
- 选定后：改剧本 → 同步分场分析（埋点/设定标注）→ git 提交，每批一个 commit
- 审查结论"无改动"也要记录（写清为什么不改，防重复审查）

### 创作质量手术（2026-08-07 伏妖记实战验证——用户核心纠偏）

**铁律：质量 ≠ 数据。** 用户明确纠正过「重点不是数据，是创作质量」——不要数场次/算时长/对比范本场次数（罗生门406场是分镜风格，饮食男女152场是动作节拍，都不是场次堆出来的）。该查的是**该重的戏写轻了没有**。

#### 七个质量维度（逐场过）

1. **说了 vs 演了**：内心独白（"她伸出手，又缩回来"×2）→ 换成外在动作/画面闪现。莲儿偷丹：闭眼→再睁开是花莲被砸死的画面（"花莲的脸。花莲的叫声。"）——罪恶感有了锚，观众看到为什么偷。
2. **对白不复述画面**：遭遇已经用画面演过（镜中映画/闪回），后面的对白**不能再说一遍**。用户连问「遭遇是靠对白展现的？」就是抓这个——独白只补"新信息"（此刻的恨），不重复"旧信息"（过去的遭遇）。删掉"我师傅养我二十年……"整段，因为第17场画面已经给过。
3. **反派情绪触发点**：软→狠必须有个触发（看见男主手背灼印"被护过的印记"→看自己的手"空空的，没有疤没有印"→嫉妒点燃→才狠）。**狠应递增不反复**（范本：七宗罪Doe从头到尾是布道者）。没有触发的软硬反复=节奏乱。
4. **信息差三层结构**：观众/反派/主角各知道什么，写清楚。镜妖由妒生恨：观众知道（交叉剪辑师傅点灯）、镜妖察觉（"亮得有人气，像有人守着"）但**张了张嘴又闭上了**（不说破=不成全他的幸福）、男主不知道（始终）。"张了张嘴又闭上"比直接点破狠十倍。
5. **道具贴人物**：道具不是考据问题，是**人物气质**问题。烟袋不贴（市井老江湖 vs 深不可测的执棋者）、铜钱不贴（算卦先生）、拂尘不贴（摆拍）——**深不可测的人手上干净，不需要道具**。道具必须**有功能**（桃木剑=吃饭家伙、陶罐=封印法器/母亲遗物），装饰性道具全删。松弛感靠行为（给小白留吃的/缠绳子嘟囔），不靠物件。
6. **宗教敏感处理（备案审查）**：去**明确宗教身份/场所/行为**（道髻→白发束起、道观→荒居、念经→陪她坐几天、修行→本事）；保留**民间信仰**（山神庙/香火/泥塑）因**批判立场明确**（伪神吃祭品→被铲除）反而安全；伏妖师职业工具（桃木剑/符袋）属民间传说体系，保留。
7. **拆场按戏剧节拍**：一场 296 行塞 8 个高潮节点（吞丹/身份/我信他/渡妖力/反杀/黄光/封印/你孤单吗）= 观众情绪被连续冲击。拆成 5 场各一个节拍（破封/逼问/渡妖力/反杀/你孤单吗），**内容零删减，只切节拍**。Python 脚本按节点行号切片（`grep -n` 定位关键台词行号 → 切片 → 验证总行数守恒 + 每个新场以完整节拍开头 + 关键金句在位）。原场次后续场顺延（第19场→第23场），分场分析/大纲的场次引用同步更新。**拆场后文档同步三处**：剧本（拆）+ 分场分析（新场次条目，含节拍/时长/知识库标注）+ 大纲（场次引用语义更新，如"渡妖力"→20场）——飞书正本重导 + Obsidian 归档提交。

8. **反派形象设计：时间两态对照 + 恨之遗物**（2026-08-07 伏妖记实战）：
   - **不要"童态"**（天真/可怜的小孩没看点，且会与"孩子的信"类角色撞型）——反派的看点是**恨**。设计**同一张脸的两个时间切片**：被背叛的瞬间（她最后的笑/梳头的手掐进头顶）vs 现在的她（眼里十八年的恨）。观众在心里把两张脸叠起来：她曾经也会笑。
   - **恨之遗物**：反派杀了背叛她的人后，把其头颅做成法器/供品随身携带（白骨化不血腥，像旧法器）——恨的物证。关键写法：①首现即立（宫阙正位供台，眼窝正对殿门）；②与往事影像并置（头颅眼窝对着老道影像——观众自己解码"这就是那颗头的主人"）；③崩塌时收尾（"她看了一眼，没捡。她住不起这座宫阙，可她带着他的头，住了十八年"——梦碎了恨还在）。
   - **与主角方遗物对照**：反派的恨之遗物 vs 主角方的守护遗物（母亲发丝做的长明灯/故人遗物）——同一场交叉剪辑里两件"遗物"并置，一个为守护而燃，一个为仇恨而存。

#### 重复检查（全篇扫一遍）

- 同一句台词/意象出现两次=稀释（"运气好"vs"有福气"、"她救过的人比你见过的人都多"×2、"叶子颤了一下"×2）——**删弱的那次，强的留下**
- "信"字情感词在情绪段堆积（5次）→ 情感交付**一次说透**（小偷家族·最轻动作），堆到麻木=稀释
- "不是X是Y"句式：作者旁白里=AI味；**人物对白/画面递进里=合法**（"眼前不是溪水，不是月光——是庙门口的石阶"），逐条判断不误删

### 去AI味实操清单（用户判定标准，实战验证 12 处）

| 病症 | 模式 | 处理 |
|---|---|---|
| 叙事者解读心理 | 「他明白了」「她自己没察觉」「像是问X又像是问Y」「久到XX以为他要说什么」「太虚弱了他没能醒」 | 删或行为化（手按心口皱眉/他站在屋里没动） |
| 不是X，是Y句式 | 「她不是妖的狰狞，是一张人的脸」 | 正文删；**对白金句保留**（如「他不是算好的。他是信的」） |
| 效果预判 | 「疼得倒吸一口气」「吓得往后缩」「吓傻了」 | 删程度标签，动作自己说话（倒吸一口气/往后缩） |
| 括注解读 | 「（像在辨认什么）」「（眼神里有说不清的东西）」 | 行为化（凑近那颗丹，停住） |
| **刻意保留** | 画面比喻（像烧焦的树瘤/像落进干涸的河床）、重复即弧光母题（孽徒/带着吧/我是妖）、角色台词里的「不知道」（对白非叙事者） | 不是 AI 味，勿删 |

扫描命令：`grep -n "他明白了\|没察觉\|像是问\|疼得\|吓得\|吓傻\|不是.*是.*" 剧本.md`——命中后逐条判断病症 vs 保留项。

## 交付到飞书文件夹（2026-08-06 实测）

**⚠️ 文档定位（用户纠正定稿）：飞书 Hermes 文件夹下的文档是正本，不是副本**（用户原话「飞书文档不是什么副本，这是正本」）。Obsidian 项目目录是 git 归档层（版本历史/过程留痕），不是权威源。创作成果以飞书正本为准——交付/更新后飞书必须是最终形态，Obsidian 归档配合记录。

剧本打磨完，用户会给一个飞书云盘文件夹链接（`/drive/folder/<token>`）让放入创作文档。工作流：

1. **整理 5 份文档**（用户明确要求的结构）：剧本正文独立一份；其余（项目创作纲领/故事概述/人物小传/时间轴/分支管理）**归并为一个项目文档**——用户原话「剧本外的都归到一个文档中」，不要拆散多份
2. **导入前处理**：md 文件要去掉 frontmatter（`--- tags:...---` 块会显示为裸文本）；用 `tr -d '\r'` 去 CRLF
3. **导入 docx**（bot 身份，串行执行——同位置并发会报 `232140101`）：
   ```bash
   lark-cli drive +import --file "x.md" --type docx \
     --folder-token "<FOLDER_TOKEN>" --name "《片名》剧本正文" --as bot
   ```
   成功后返回 `permission_grant.status=granted`（自动授予 full_access）+ url
4. **替换旧文档**：删旧建新（导入不支持覆盖）——`drive +delete` 参数是 **`--file-token`** 不是 `--token`（否则报 unknown flag），需 `--yes` 确认：
   ```bash
   lark-cli drive +delete --file-token "<TOKEN>" --type docx --yes
   ```
5. **验证**：`lark-cli drive files list --params '{"folder_token":"<TOKEN>","page_size":50}'` 确认落位与数量
6. **坑**：临时工作目录可能被终端进程占用删不掉（Device or resource busy）——用 `python -c "import shutil; shutil.rmtree(...)"` 兜底

## 结构化总结模板

面向影视从业者：简洁中文、下结论带证据（引集数/场次）、高信息密度。

1. **身份卡**：年代 / 类型 / 集数 / 一句话故事
2. **单元结构表**：`| 单元案件 | 集数 | 内容 | 埋的钩子 |`（多案剧按案件分列，钩子=后文回收的伏笔）
3. **钩子/伏笔追踪**：每条伏笔（身世、妖丹、角色重伤等）在哪些集埋下、哪里回收、是否闭环
4. **完整度检查**：✅ 已闭环项 / ⚠️ 小问题（错别字、场次标注错误、前后矛盾、续集钩子）
5. **收尾**：主动问下一步方向（整体评估/改某段戏/拆案/分镜/提示词），不给用户布置作业

## 用户偏好

- 全文先落盘再读，避免反复网络调用
- 回复结构化、信息密度高，不罗列全文，用表格呈现多单元结构
- 读完不问"要不要我干嘛"，而是给出可选项让用户定方向
