# 项目级 OV 总览落地工作流

> 当用户要求"整理 X 项目总览、进度等，放到 OpenViking"时使用。
> 配套主 skill：`hermes-runtime-pitfalls`（OV 运维章节）。

## 触发场景

- 用户原话含"放到 X 项目 / 整理项目总览 / 落 OV / OV 入口 / 跨会话召回"
- 项目有**飞书正本** + **历史版本/旧版** + **团队协作需求**
- 跨多设备访问同一份项目资料

## 第一步：向用户拍板当前正本（不可跳）

**铁律**：用户拍板"以新的 X 为准"时，**必须**让用户**显式给**新正本的 URL/token，**不能**从 OV 旧事件卡/MEMORY 推断。MEMORY 里看到的"X"和用户当下指的"X"可能不是同一个东西（版本已迭代多次）。

**问询要点**：
1. 权威正本位置（飞书 URL/token 或其他平台）
2. 旧版状态（淘汰？参考？保留多久？）
3. 覆盖范围（项目总览要不要全量包揽？还是精简版？）
4. 其他工具分工（Obsidian 退役？保留双写？写入策略？）

**反面案例**（2026-09-03 伏妖记）：agent 去看 OV 事件卡推断"正本是 EsMD/NSZK"→ 实际是 v2.1.4 旧版 → 用户已经完成 9/2 大重做，新正本是另两个 URL。

## 第二步：选择目录位置

| 资产类型 | 路径 | 触发词 |
|---|---|---|
| **项目级总览** | `viking://resources/projects/<项目名>/` | "项目总览" "项目入口" |
| 一次性任务归档 | `viking://resources/_archive/<日期>-<主题>/` 或 `viking://resources/<任务名>/` | "归档" "存档" "留档" |
| 团队手册/规范 | `viking://resources/_team-handbook/` | "团队手册" "规范" |
| 测试资源 | `viking://resources/_test/` 或 `viking://resources/test/` | "测试" "样本" |

**混用风险**：把一次性任务归档到 `projects/<项目>/` 会稀释项目总览的 recall 精度。

## 第三步：目录结构（推荐 13-15 份文档）

```
viking://resources/projects/<项目名>/
├── README.md                           # 总览入口（最关键）
├── 00-项目元数据.md                    # 单页可读入口
├── 01-核心设定.md                      # 世界观/规则/纪律
├── 02-人物小传.md                      # 角色列表
├── 03-故事线.md                        # 故事梗概/结构
├── 04-分场大纲.md                        # 场次清单
├── 05-场景与美学.md                    # 场景视觉
├── 06-美术设计.md                      # 视觉/光影/调色（可选）
├── 07-配乐与声音.md                    # 声音/主题音乐（可选）
├── 08-剧本创作方法论.md                # 方法论（可选）
├── 09-进度时间线.md                    # 版本演进
├── 10-创作复盘.md                      # 复盘/经验
├── 11-决策留档.md                      # 拍板记录
├── 12-待定与OpenItems.md               # 未决项
└── README-过期记忆索引.md              # 旧版降权说明（如适用）
```

## 第四步：每个文档必含的顶部元信息

```markdown
# 《X项目》核心设定

> 来源：新正本 <token/URL> revision N
> 旧版 <token> 已<淘汰/保留参考>
> 创作阶段：<重做中/锁定/拍摄> | <日期>

[正文]
```

**关键**：每篇文档头部必须明确"以哪个版本为准"，agent 单看一个文档也能立刻定位。

## 第五步：批量上传技巧

**重要性倒序**：
1. README.md + 00-项目元数据.md 先传（最关键）
2. 02-人物小传.md + 03-故事线.md 次之
3. 其余子文档并行传

**调用方式**：
```python
viking_add_resource(
    to="viking://resources/projects/<项目>/README.md",
    instruction="<一句话描述>",
    reason="<为什么",
    url="file:///C:/Users/.../<file>.md",
    wait=False,  # 关键：wait=False，避免 L0/L1 索引超时
)
```

**串行 + sleep 节奏**：每批 ≤4 个文件，每批后 `sleep 10-15` 让摘要跟上。

## 第六步：验证矩阵（落地后必跑）

| 验证项 | 命令 | 通过标准 |
|---|---|---|
| 目录树可见 | `viking_browse path=viking://resources/projects/<项目>/` | 列出所有上传的文档（abstract 可能 is not ready） |
| 关键词召回命中新版 | `viking_search("项目名 + 新版核心关键词")` | 命中 `viking://resources/projects/...` 的文档，score ≥ 0.45 |
| 关键词召回压制旧版 | `viking_search("项目名 + 旧版核心关键词")` | 新版事件卡/总览 rank 1-2 |
| 过期说明召回 | `viking_search("项目名 + 已过期/淘汰")` | 命中过期说明事件卡 |

**关键词命中策略**：
- **新版关键词**：当前正本的角色名 + 术语
- **旧版关键词**：被淘汰的角色名 + 术语
- **不要试图单一关键词召回同时命中新旧**——会让 agent 误判权威

## 第七步：旧版降权处理

**踩坑教训**（2026-09-03）：用户拍板"旧版少许参考价值" → 我一开始想给每张旧实体卡加"过期标记"——实际验证 OV `viking_remember`/`update` **不能修改存量卡内容**（只能新增或 `viking_forget` 删除）。

**真正能用的降权手段**（按效果递增）：
1. 写新版 README + 元数据**顶部权威台账**让 recall 时关键词走新正本路径
2. 给新版加更专更全的关键词命中，让新版分数自然超过旧版
3. 给 OV 加一条**过期说明事件卡**（关键词密集 + 指向新版 README）——实战有效，把新版排在首位
4. **批量 `viking_forget` 旧版重复卡 + 留 1 张 viking_remember 快照卡**——**最彻底**。2026-09-03 伏妖记实战：删 60+ 张旧版重复卡后，旧版关键词 recall 完全压制，搜"伏妖记 镜妖 陆老邪"只命中新版事件卡 + 旧版快照卡 + 新版文档

**批量 `viking_forget` 操作要点**：
- 每次 `viking_forget(uri)` 单次执行，**不能批量**（不像 `viking_add_resource` 可以 `wait=false`）
- 每个调用返回 `{"status": "deleted", "estimated_deleted_count": 1}` —— 0 也可能成功（文件已被前置清理）
- **保留快照策略**：删 12 张同主题事件卡之前，先用 `viking_remember` 一张合并版快照（带角色表+版本时间线+新旧版对照），快照 URI 自身成为"旧版唯一可检索入口"
- **子代理盘点模式**：批量 forget 前，先派一个子代理跑 `viking_search` + `viking_browse` 全量盘点，输出"可合并/可过期/可清理"清单，避免 agent 自己在主线程漏删或误删

**过期说明事件卡模板**（`viking_remember` category=event）：
```python
viking_remember(
    content="<日期>用户拍板<X项目>大重做启动：新正本以飞书<新token1> + <新token2>为准。"
            "旧版<旧token1>（v2.1.4，23场）和<旧token2>已淘汰，少许参考价值。"
            "新版反派Boss从<旧A>改为<新A>；师父从<旧B>改为<新B>；..."
            "OV项目总览入口：viking://resources/projects/<项目>/，含README/00-12共<N>份文档+过期记忆索引。"
            "所有<v2.X>时代的事件记忆/实体卡/偏好已标记为过期；以新版为准。"
            "如需查旧版具体设定对照可参考viking://resources/projects/<项目>/README-过期记忆索引.md。"
)
```

**实战数据**（2026-09-03 伏妖记）：
- 搜"伏妖记 金翅鸟素鸢 暮云亭 澄阳观 依依" → 新版事件卡 rank 1（0.52），新版核心设定 rank 2（0.512）
- 搜"伏妖记 镜妖 莲儿 陆老邪" → 旧版事件卡压制（OV recall 主要看相关性，旧版实体卡短小精悍分数高）

## 第八步：Obsidian 写入退役（可选）

如果用户拍板"Obsidian 写入退役"，**逐**必须**先确认范围**（是单一项目，还是所有项目），再执行：

1. **标记只读归档**：在 Obsidian 项目目录加 `_归档说明.md`
2. **更新 Obsidian 现有笔记**：顶部加只读归档标记
3. **git 提交归档标记**：`git commit -m "归档(<项目>): 退役Obsidian写入，标记为只读归档，OV主写"`
4. **OV 写铁律持久化**：`viking_remember` category=pattern 内容 = "凡涉及 X 项目的新内容只走 OV"
5. **更新 OV README 顶部**：加"Obsidian 写入已退役"声明

**撤销/调整边界**：用户改主意时同步改三处（Obsidian `_归档说明.md` + OV README + pattern 记忆）。

**陷阱**：
- ❌ **一刀切所有项目**：用户拍板"退役 Obsidian 写入"可能只是某一个项目（如伏妖记），不是所有项目
- ❌ **删 Obsidian 内容**：只标记只读，不删内容（保留 git 历史）

## 第九步：触发更新条件（项目级总览）

未来任意触发更新：

| 触发 | 动作 |
|---|---|
| 正本 revision 推进 | 同步更新 README + 元数据 + 进度时间线 |
| 用户拍板新决策 | 更新决策留档 + 必要时分场景/分场 |
| OpenItem 解决 | 更新待定 OpenItems + 必要时分场景/分场 |
| 创作阶段升级 | 新建对应阶段文档（如分镜、美术） |
| 用户主动更新指令 | 全套同步 |

## 反面案例

- ❌ **从 OV 旧事件卡推断当前正本** → 9/3 伏妖记案例：用户已经完成 9/2 大重做，但 agent 看 8/28 事件卡推断 v2.1.4 是新正本
- ❌ **多个文档混传** → 大文件 L0/L1 摘要生成延迟 30 分钟+，recall 时可能 abstract is not ready
- ❌ **加过期标记但不写新台账** → recall 时旧版仍可能压制新版
- ❌ **直接删除旧记忆卡** → 用户拍板"少许参考价值"不等于"删除"
- ❌ **未 git 提交就标记只读归档** → git 历史没记录
- ❌ **项目级总览与一次性任务归档混用目录** → recall 精度下降
