# 技术工具用法文档(How-To / Usage Manual)

撰写"已选定工具/服务的实操说明书"——用户**已经决定用哪个**,现在要知道**怎么用**。

## 何时用

- 用户要求写"X 使用说明书""X 详细用法""X 怎么用"
- 用户输入为某工具/API/服务的具体名称 + "说明书/用法/教程"
- 输出形态 = 单份 Markdown 文档,目标读者会用命令(`curl`、Python 客户端)直接跑

### 何时不用

| 触发 | 用什么 |
| --- | --- |
| "对比 X 和 Y 选哪个""评测一下" | `analysis-report` |
| "X 项目文档""这个项目的开发文档" | 项目文档 skill(项目级) |
| 给创作文档写"哲学/思路/设定"(剧本大纲/技法卡片) | `screenplay-iteration-management` 等创作类 skill |
| 内部 wiki 风格"团队 Onboarding""X 操作 SOP" | 走团队知识库,跟产品用户文档不同形态 |

## 用户对该类文档的硬约束(2026-08-26 实测归纳)

### 1. "实际地详细地用法"是核心

用户原话"我需要实际地详细地用法"。两次写都被否 → 必须遵守的几条:

- **每个命令前必须有判断标准**(为什么要这么写),不是只贴命令
- **可复制运行的命令占主体**(curl / Python / 等),不是概念段落
- **字段表 + 实战值**(默认值 + 实战推荐值)代替字段语义解释
- **失败诊断表**(现象→查什么→修复方法)代替原理描述

### 2. 不要输出"概念全表"

第一次输出被否的关键错:**罗列全部 30 个端点 + 字段语义解释**——这种是"API reference",不是"使用说明书"。

- 只列**核心端点**(日常会用的 6~10 个,不超过用户的注意力带宽)
- 边缘端点归"附录速查表",不展开
- 原则:**用户能复制跑 = 80%,理解原理 = 20%,附录速查 = 5% 以下**,比例错就是"全表"

### 3. 命令必须基于实测

- 服务/URL/端口/字段**不能凭印象**——必须用工具验证(终端直连、`openapi.json`、health 端点)
- 不能验证的字段标"待证"
- 必须告诉用户 v1 / v2 之间的差异

### 4. 不重复发明轮子

正文主体 = 你的实操判断;字段全表 = 链回 OpenAPI / 官网。OpenAPI 不会过期,说明书会过期——分工要明确。

## 输出文档的最小必要结构

不是"模板",是实证有效的章节骨架。**实际章节数 ≥ 7,≤ 12**,少了像粗稿、多了像论文。

```
0. 元信息(版本/部署/作者/一句话定位)+ 怎么读这份说明书(跳读索引)
1. 30 秒入门(三行内能跑通的最小命令——search/add/工具调用,挑一)
2. 什么时候用 vs 不用(决策点,和替代物对比)
3-N. 按"场景"组织主体(写入/检索/管理/多cube/chat 等)
N+1. 失败诊疗(分现象给查→修复对的顺序)
N+2. 最小必要原理(只讲理解所需的,不讲"是什么")
附录 A. 字段速查表(命令能用上,无废话)
附录 B. 踩坑表(用户实战累积,带现象/原因/解决)
附录 C. 这份说明书之外的真相(=链回 OpenAPI/官方文档,提醒"说明书会过期")
```

## 关键章节写法

### 30 秒入门(v1 的正确形态)

**正确**(2~3 块,各自完整能跑):
```bash
# 写一条事实
curl -X POST http://...  -d '{ "messages":[...] }'
# 搜一句
curl -X POST http://... -d '{ "query":..., "user_id":... }'
# 用内置工具(最常用)
memos_search(query=...)
memos_remember(content=...)
```

**错误**(被否的 v1):先写"MemOS 是什么"+"30 端点 4 大类"+"核心抽象"——这是 reference,不是入门。

### "什么时候用 vs 不用"表

```
| 该用 | 为什么 |
| 不该用 | 替代物 |
```

两张对照表。**用户决策第 0 关**——他要先判断这是不是对的事。

### 场景主体(每节一个动词)

每节起头 = 一句话说明"什么时候做这事"。然后:
- 1 个完整可跑的命令(curl 或 Python 一键封装)
- 1 个判断法(如"三步过滤"判断该不该写)
- 1 个注意事项("写后 30 秒索引,要 sync 才会立刻可读")

**严禁**:每节把概念讲一遍再讲命令。

### 失败诊疗

```
| 现象 | 先查 | 再查 |
| search 返回空 | readable_cube_ids 是否包含真写过的 cube | user_id 是否一致 |
```

每行一个**用户实战中真实遇到**的问题,而不是"理论上可能"的问题。

### 附录 C 必备

每个说明书都会过期——**必须在末尾明说"以 X 为准,说明书会过期"**,并写明那句话的真实指向(URL / OpenAPI 路径)。

## 用户偏好的 markdown 写作铁律

| 偏好 | 体现 |
| --- | --- |
| 排版紧凑 | 表格代替段落;小标题多 |
| 中文为主,字段名英文 | `info` / `custom_tags` / 端点路径 = 英文;解释 = 中文 |
| 命令块完整可复制 | `bash` 代码块完整带 `-H ` / `-d`,可粘就跑 |
| 元信息/版本号必须放开头 | "2026-08-26 实测,基于 v1.2.3"在第一屏 |
| 命令中穿插判断标准 | 不仅是命令,还有"什么场景用这条命令""为什么这样选" |

## 写作完成前的自检清单

- [ ] 没说"是什么",只说"怎么用"+ "为什么"
- [ ] 30 秒入门可以让人**不读其它内容**就跑通最小流程
- [ ] 主体场景数 ≥ 5,每节 = 一句话判定 + 1 个命令 + 1 个判断 + 1 个注意
- [ ] 失败诊疗每个案例都来自真实踩坑(不是"理论可能")
- [ ] 字段速查表里**没有语义解释**——只有字段名 + 实战值
- [ ] OpenAPI 入口明示,说明书与官方文档的分工说清
- [ ] 标题带"使用说明书"/"用法"+ 日期 + 版本号

## 常见反模式(多次被否)

| 反模式 | 被否原因 |
| --- | --- |
| 概念全表 = 6 章端点解释,2 章用法 | 用户原话"我需要实际地详细地用法"——6 章概念是"理论全",2 章用法才是"实际" |
| 文档开头一大段"X 是什么" | 用户已经知道 X 是什么(否则他不会让你写说明书),要直接给命令 |
| 命令仅有 yaml/json 结构,不写完整 curl | "可复制可运行"必须是完整命令,不是"省略号"型 |
| 字段表只有字段名+类型(没有实战值) | 用户实战缺的不是字段名(查 OpenAPI 就行),而是"实战怎么填" |
| 大量引用官方文档当原文 | 复述官方文档=用户要请你干嘛?他可以直接读官方——只能写**判断标准 + 实战值 + 坑** |
| "会用即可,原理不用懂" | 不需要原理不等于不需要心智模型——保留"最小必要原理"一节 |
| AI 感评述句("这意味着..." "从而实现..." "象征着...") | 详见 `analysis-report` §AI 感自检 |

## 配套纪律

### 写入位置

- 主工作区 `Documents/Hermes/分析/`(与 `analysis-report` 同级)
- 文件名:`<工具名>使用说明书-<日期>.md`

### 不做的事

- 不写两份"完整版"和"精简版"——单文档即可,场景分节够用
- 不写"教程式分步骤"——使用说明书不教基础,**默认用户会用工具**
- 不输出"长篇概念章"("架构""原理""设计"等章节)——保证用法占比 ≥ 70%
