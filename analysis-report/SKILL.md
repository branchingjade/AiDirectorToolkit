# 分析报告撰写规范

面向该用户的调研分析报告产出标准。用户是电影后期从业者，偏好实战导向、快速决策。

## 触发条件

- 用户要求对某技术/工具/方案做「分析」「对比」「调研」「评测」「选型」
- 用户说「帮我看看 X 和 Y 的区别」「X 有哪些方案」
- 用户扔来一个 GitHub 链接说「对比下 X 项目」「X 怎么样」——**默认解读 = 拿 X 和同类开源项目横向对比**（对标，2026-08-11 两次纠正实证：先误读为单项目分析被纠正「对比项目」，再被纠正「对比同类项目」）。此时动作是：找同类 → 抓数据 → 产出对比表，不是单项目解读
- 用户说「在右侧预览窗」「预览」= 交付形态用 HTML 文件 + open_preview 工具（见下）

## 核心原则

### 1. 单文档输出（不做增量迭代）

**❌ 错误**：先出一份初稿→用户纠正→出第二份→用户再纠正→出第三份，目录里堆了 3 个 md。

**✅ 正确**：
- 第一轮先确认范围和重点（必要时用 clarify），再动手写
- 如果用户中途纠正范围，**替换**原文档而非追加新文档
- 最终只保留**一份**成品

### 2. 精简 > 详尽

用户明确偏好「更精简」。一个 7KB 的表驱动文档优于 40KB 的论文式文档。

**精简手段**：
- 用表格代替段落（对比信息天生适合表格）
- 用决策树代替分场景长文
- 用一句话总结代替展开论述
- 砍掉学术历史背景（除非用户明确要）

### 3. 结构化模板

```
# [主题]：[范围限定词]

> 日期 | 面向场景

## 一、速览：选什么？（最重要——直接给答案）
| 场景 | 首选 | 备选 |

## 二、主体对比（表驱动）
| 项目 | 维度1 | 维度2 | 维度3 | 一句话 |

## 三、优缺点（★/✗ 格式，不展开）
**优点**：★ 要点
**缺点**：✗ 要点

## 四、决策路径（决策树/流程图）
├─ 条件A ──→ 方案1
└─ 条件B ──→ 方案2

## 五、硬性门槛（如适用）
| 方案 | 最低配置 | 推荐配置 |
```

### 4. 实战导向

- 每个结论要能落地：知道「选什么」「怎么装」「跑不跑得动」
- 用户是电影后期从业者，优先考虑 Resolve 集成、视频时域一致性
- 关注价格（买断 vs 订阅）、硬件门槛

## 同类项目横向对比（GitHub 仓库对标，2026-08-11 实证）

用户说「对比下 X 项目」= 对标同类。完整流程：

1. **找同类**：`gh search repos "关键词" --sort stars --limit 15 --json fullName,stargazersCount,description,language`（gh CLI 直接可用，比 web_search 准）
2. **抓核心元数据**：GitHub API 批量抓 stars/forks/license/语言/创建与活跃时间——`curl -s "https://api.github.com/repos/{owner}/{repo}"`，一次循环抓全部候选
3. **抓 README 定定位**：用 `raw.githubusercontent.com/{owner}/{repo}/{default_branch}/README.md`。⚠️ **默认分支不一定是 main**——先查 `default_branch` 字段（腾讯的 TencentDB-Agent-Memory 默认分支是 `feat/server_team`，用 main 抓 404）。`/tmp` 在 MSYS 下不可写，curl -o 要写工作目录
4. **产出对比表**：定位一句话 + 核心能力对比表（记忆形态/协作共享/权限/冷启动/跨框架/检索/部署），差异化结论单独成节
5. **交付**：预览窗形态 = 写 HTML 文件（暗色 #08090a 系、表驱动、标注数据来源）→ `open_preview`（deferred tool，tool_search 加载）打开本地 HTML 路径。用户偏好预览窗直接展示，不只看聊天文字

**结论句式**：结尾给「对你的参考价值」表——用户视角（现状 → 对应物 → 可借鉴度），这比抽象评价有用。

## 存放位置

- 优先写入 Obsidian vault（KnowledgeBase 根目录）
- 文件名：`[主题]指南.md` 或 `[主题]对比.md`
- 不要嵌套在 `Obsidian Vault/` 子目录下

## 数据溯源

用户关心数据从哪来的。报告中每个工具/方案的数据需标注来源类型：

- **网页验证**：成功访问官方页面提取的信息
- **训练知识**：模型预训练数据中的记忆（可能过时）
- **推断**：基于已知信息的合理推导（需明确标注）

用户问「资料在哪些地方找的」时，直接说明每项的来源。不要模糊带过。

## 研究过程常见障碍

搜索引擎（Google/Bing/DuckDuckGo）经常对自动化请求返回 CAPTCHA/Cloudflare 验证。应对策略见 `references/web-research-patterns.md`。

火山引擎/BytePlus 等国内云平台的产品页通常为 React SPA，curl 返回 JS 壳，browser 工具渲染不稳定。此类页面 curl 返回 200 不等于内容可提取，应标记「需本地浏览器打开」。

## 反模式

- ❌ 产生多个版本文档（v1/v2/v3）
- ❌ 学术论文式长文（用户会说「整理笔记，产出了好几个文档」）
- ❌ 没有决策路径（用户要的是「我该选哪个」，不是百科全书）
- ❌ 结论藏在文末（速览表必须放最前面）
- ❌ 信息来源不透明——用户会追问「在哪些地方找的」，报告中每个工具的结论需要能追溯到具体来源（URL/产品页/训练知识）

## AI 感自检（用户明确反馈过「文档 AI 感有点重」）

给用户交付的任何文档（含创作类文档：剧本大纲/人物小传）写完后自查，四类 AI 味必须清掉：

1. **评述腔**：影评人式注释，如「——他的局开始走」「——兔妖篇开始」「价值观冲突开场第一拍就响」。只写发生了什么，不写「这象征着什么」。
2. **「不是X，是Y」句式**：如「不是抛弃，是布棋」「不是听不懂，是恶对她无效」。直接陈述事实本身，不要先否定再转折。
3. **术语堆砌**：弧光、感情语言、跨场追踪、具象化、世界观锚点等抽象词连排。工作标记可留一两个，满篇都是就变论文。用大白话（「他怎么表达感情」「这个人物的变化」）。
4. **重复强调**：同一金句/结论出现两次（如「全片唯一让镜妖沉默的话」写了两处）。一处说透即可。

**扫描用正则（2026-08-10 实测）**：`不是[^，。]{2,12}[，,]是` 抓「不是X是Y」；空话词清单 `总而言之|总的来说|值得一提的是|不难发现|赋能|抓手|闭环|极致体验`。⚠️ **裸破折号「——」不当 AI 味信号**：表格式文档里破折号大量用于表格解释/来源分隔（实测 43 处命中全为合理用法），只能人工甄别，不能当正则信号。扫描完区分「表内解释性破折号（合规）」与「影评式评注破折号（要删）」。

## 权威背书标准（用户原话「要有权威背书」）

分析/总结/设计类文档的每个结论必须有出处（机构名+文章名+年份，或书+作者+年份），并标注来源类型：**训练知识**（经典著作/官方文档，稳定）/ **网页验证**（实访页面）/ **实测**（本机验证）。设计类文档额外要求「实战对照」表：把用户既定偏好逐条映射到权威依据（如「记忆上次状态 → Nielsen #6 识别优于回忆」），可直接当决策引用。没有出处的结论会被用户打回。

## 陷阱

### SPA 产品页无法被 curl/Hermes browser 渲染

很多现代产品页是 React/Vue SPA，curl 只拿到 JS 壳，Hermes browser 工具也可能渲染空白。此时用 **Kimi WebBridge** 操作用户真实 Chrome 访问页面：

```python
# execute_code 写临时文件 → curl --data-binary @文件 → 删文件
# 用 evaluate + innerText 提取 SPA 渲染后的文本内容
```

详见 `kimi-webbridge` skill 的 execute_code 模式。

### 产品页可能不存在/已下线

不要凭训练知识假设某个 URL 存在。对比报告中的每个产品，如涉及具体页面，应先验证是否能访问（返回 200 且非 404 SPA 路由）。本 session 中 `bytedance video enhancer` 产品页实际返回 404，视频超分能力嵌入在 Seedance 2.0 / ModelArk 中而非独立产品。
- ❌ 不标注数据来源（用户会追问「在哪些地方找的」）
