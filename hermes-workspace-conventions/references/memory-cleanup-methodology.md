# Memory 清理方法论

Memory 臃肿或污染时执行系统性清理。

## 核心原则

### 分类铁律（写入门禁）

写 memory 前逐条确认三条，全通过才写：
1. skill 里已有同样内容？有 → 不写，patch skill
2. 是版本快照/TODO/任务进度？是 → 不写，记 Obsidian
3. 不记会犯错？否 → 不写

有一条不确定 → 不写。

### 行为指令 vs 决策知识（2026-07-24 重构）

| 类型 | 放哪 | 例子 |
|------|------|------|
| 决策知识（不记会犯错的事实） | memory | cron 用 LLM 驱动、禁杀全盘 Chrome |
| 行为指令（做之前对照的规则） | skill | 输出中文、自检、分类门禁 |
| 人格声明 | SOUL.md | 诚实、直接 |

**行为指令放在 memory 里不会被触发**：memory 处于系统提示「背景知识」层，agent 注意力集中在 skill 上，不会主动扫描 memory 找 checklist。

### 不要凭经验判断"过时"
- **禁止**在没有证据的情况下标记条目为"可能过时"
- 用户说"还在用"= 还在用，不需要追问

### 不要只分析不执行
- 列出问题后必须立即执行清理

### 已指向skill的条目直接删
- 如果 memory 条目末尾有 `→详见xxx skill`，且 skill 存在且完善 → 直接删

### 描述性内容不属于 memory
- "AI提示词助手定位：优化器"——这是描述，不是决策铁律
- 判断标准："不知道会犯错吗？"

## 流程

### 1. 审计
逐条过，判断归属：
- **决策知识**（不知道会犯错）→ keep
- **行为指令**（做之前对照）→ 搬 skill
- **已指向skill** → remove
- **描述/配置快照/项目状态** → remove

### 2. 逐条确认
- 展示完整内容 + 理由
- 用户说"删"才执行
- 不要批量操作，不要催促

### 3. 执行
- 批量清理（>3条）用 `write_file` 一次性写入干净版
- 少量条目用 memory 工具逐条删
- 不要反复重试同一操作

### 4. 验证
- 确认删除的条目已有 skill 覆盖
- 确认 skill 完善（`skill_view` 验证）

## ⚠️ Memory 工具子串匹配陷阱

`memory(action='remove')` 用子字符串匹配。短字符串可能误命中多条。批量清理优先用 `write_file`。

## 根因：为什么 memory 反复被污染

### 摩擦不对称（2026-07-24 诊断）

| | memory | skill_manage |
|---|---|---|
| 写入成本 | 一行 `add` | 需匹配 `old_string` |
| 失败风险 | 几乎为零 | 匹配失败就报错 |

agent 认知负荷高时总结冲动自然流向零摩擦的 memory。**不是规则不够好——是结构造的。**

### 注意力焦点（2026-07-24 诊断）

行为规则在 memory 里不会在关键时刻被检索。agent 注意力在 skill 当前步骤上，memory 是背景知识。→ **行为指令必须放 skill。**

## Skill 清理方法论（2026-07-24）

清理 hermes-workspace-conventions skill 时确立的标准：

| 删什么 | 原因 |
|--------|------|
| 重复内容 | 同一件事在两个地方讲（如自检→修复闭环 vs 自检流程） |
| 过时引用 | "本 session"/"本次会话"——无上下文，无效 |
| 过时数据 | "13条决策铁律"→现在是7条 |
| 跑题内容 | MoA、Bilibili、write_file——不属于工作区约定 |
| 环境快照 | "当前配置了 MiMo v2.5"——不是约定 |
| 展开过度的诊断 | 摩擦不对称写了 41 行→浓缩为 5 行陷阱条目 |
| 一行占一节 | "Obsidian Vault 维护"——skill 引用就够了 |

## 本次清理记录（2026-08-10，两轮瘦身 + 最优水位定标）

- 触发：用户「优化memory」→ 完成后追问「有hindsight的话，还要这么多吗」「MEMORY应该限制在多少最优」——架构性质疑，不是要删光，是要「该装多少」的标准
- **注入 vs 检索原理（Hindsight 替代不了 MEMORY 的根本原因）**：MEMORY 每会话开头全量注入系统提示，必在场零成本；Hindsight 是主动 recall 才命中的检索层，语义排序 + token 预算截断（实测飞书内容排第 6/10 位被桌面内容挤掉）——「不记会犯错」的决策铁律不能赌检索概率。分工定稿：Hindsight=会话细节自动记忆层（可查可召回），MEMORY=决策知识注入层（必在场）
- **最优大小标准（用户拍板方案）**：目标 ≤10,000 字符（50%）、触发清理线 12,000（60%）、config `memory_char_limit`=16,000（写满被拒→倒逼先清后写）、下限警惕 <6,000（说明铁律被误删）。依据：官方默认 2,200 定位不同不够用；2026-08-07 清理后 9,276（46%）实测健康态用了一个多月；每会话全量注入 ≈1 token/字，越长注意力稀释越严重；50% 留余量避免每月清理
- **两轮瘦身法**：第一轮=删 skill 已覆盖的整条（删前 `grep -rl` 实证，11 条：画像机制/评论会话/反爬/并行子代理/useI18n 等）+ 长条精简；第二轮=删实证数字/日期/实例细节只留「教训是什么」（「单日 18 次」「第17-18场丢了某台词」→ 只留教训），合并重复（创作评估两条合一）
- **批量替换用脚本**：10+ 处小删用 execute_code 一次性 replace（比逐个 patch 高效）；替换前打印「未命中」清单——未命中=上一轮已精简，无需处理
- 结果：19,636（98%）→ 13,997（第一轮）→ 10,818（67.6%），58 条；剩余 5 处日期均为用户原话引用/决策锚点，保留合理
- 判断：10,818 比目标高 ~800 字，但 58 条是「不记会犯错」刚性体积，再砍要动铁律正文或把环境事实下沉 skill，收益 < 风险——即本机最优实态，不硬压
- 备注：执行前先 grep config 确认 `memory_char_limit` 现值（本次发现已被并行会话/用户改到 16000，勿重复设置）
