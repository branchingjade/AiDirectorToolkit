# 飞书 ↔ Obsidian 文档关系（文档角色模型，不机械同步）

> 2026-08-06 确立（《伏妖记》项目实战，用户多轮纠正后定型）。处理任何飞书文档前先判断它的**角色**，再决定要不要同步/回写/对比。**别机械同步飞书和 Obsidian**——用户原话："行了，别同步obsidian和飞书了"。

## 文档角色三分法（编辑前先判断）

| 角色 | 特征 | 处理方式 |
|---|---|---|
| **权威源（Obsidian 项目目录）** | git 版本控制 + 完整交付物（剧本/分场分析/自审/复盘/分支管理） | 创作决策最终落这里（git 归档）；不一致时以它为准 |
| **展示副本（飞书剧本正文类）** | 从本地源导入/重导，应保持与源一致 | 源改动后重导新版+删旧 token；内容一致是目标 |
| **独立定制版（飞书项目文档类）** | 为飞书格式/读者优化（callout/whiteboard/表格），**不是 Obsidian 文档的镜像** | **不要求逐字一致，有差异是正常的；更新节奏由用户定，不机械同步** |

**关键区分**：飞书剧本正文 = 展示副本（要同步）；飞书项目文档 = 独立定制版（不同步，用户自己维护）。把项目文档当副本去"对齐/补缺"是错误前提——用户原话："飞书的项目文档是单独的，飞书定制版"、"飞书hermes文件夹下才是今天的成果"。

## 铁律（用户原话驱动）

1. **别机械同步飞书和 Obsidian**——用户明确："行了，别同步obsidian和飞书了"。两侧都可能先行编辑（"并不是一定的，我不一定先改哪一侧"），**不做"任务结束必须一致"的强制**。
2. **飞书文档可能是独立成果，不是副本**——"飞书hermes文件夹下才是今天的成果"：飞书文件夹里的文档本身可能是当日成果的权威形态，不要因为 Obsidian 是 git 归档就假定飞书文档"滞后/过时"。
3. **项目上下文要登记所有线（登记≠同步）**——飞书侧可能有用户/他人维护的其他文档（如《伏妖记》杨编精撰 = 剧集版另一条线）。用户："为什么不记呢，杨编那个是另外一个"——agent 应知道它的存在（token + 形态 + 与主线关系，Hindsight 外部记忆自动捕捉），**不要求与任何一侧对齐**；是否采纳入主线由用户定。
4. **台账记录关系，不强制一致**——项目主文档头部维护「文档权威与同步台账」：各文档角色 + token + 当前状态。它的作用是"下次任务知道有什么、各自什么角色"，不是"发现差异就去补"。

## 通用约定（项目上下文登记）

> **多平台文档关系（飞书/Obsidian）**：Obsidian 项目目录 = 权威源（git 版本控制）。飞书剧本正文 = 展示副本（保持与源一致）；**飞书项目文档 = 独立的飞书定制版**（为飞书格式/读者优化，不是 Obsidian 镜像，不要求逐字一致——有差异是正常的）。创作决策最终落到 Obsidian（git 归档）；飞书定制版的更新节奏由用户定，不机械同步。

## 操作模式

| 场景 | 做法 |
|---|---|
| Obsidian 源文件改动 | 若对应飞书文档是**展示副本**（剧本正文）→ 重导新版+删旧 token；若是**独立定制版**（项目文档）→ 不动，用户自己定 |
| 飞书文档内容过时（你判断的） | **先确认角色**：独立定制版就不算"过时"，不要主动对齐；用户要求更新才动 |
| 发现飞书有其他相关文档 | **登记进项目上下文**（token+形态+关系），不合并、不同步、不删除 |
| 改版替换展示副本 | 重新导入得新 token → `drive +delete --file-token <旧token>` 删旧 → 文件夹保持预期份数 |

## 反例（踩过的坑）

- **把独立定制版当副本去"补缺"**：飞书项目文档是定制版，却按 Obsidian 大纲当镜像去检查"缺什么补什么"——用户纠正"飞书的项目文档是单独的，飞书定制版"。
- **强制"任务结束两侧一致"**：用户最终明确"别同步obsidian和飞书了"——机械同步被叫停，纪律改为"记录角色、登记所有线、不强制一致"。
- **项目上下文漏记其他线**：飞书侧《杨编精撰》（剧集版另一条线）长期不在项目上下文里——用户"为什么不记呢"点出缺口：项目上下文要登记所有相关文档，登记≠同步。
